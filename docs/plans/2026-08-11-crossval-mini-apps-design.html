Data model

All money = integer cents, all IDs = text, all tables carry userId.

  • Auth: Better Auth's users, sessions, accounts.
  • Pricing: pricing_documents (title, customer, issueDate, status draft|finalized, stored totals: subtotal/discount/tax/grandTotal cents — recomputed server-side each write, frozen at finalize); pricing_line_items (documentId, description, quantity, unitPriceCents, discountType percent|fixed|null, discountValue (bp or cents), taxPercent bp).
  • Orders: orders (customer, dueDate, totalCents); order_line_items; payments (orderId, amountCents, paidDate, note, idempotencyKey UNIQUE). Status never stored — derived by pure function from payments sum + due date.
  • Planner: categories (name unique per user); plans (categoryId, month YYYY-MM, amountCents; unique userId+categoryId+month); actuals (multiple rows per category-month; report SUMs); period_locks (month; row exists ⇒ locked). Month granularity = "period close".
  • Shared: audit_log (userId, app, entityType, entityId, action, detail JSON, createdAt) — written in the same transaction as the mutation. Logs finalize, duplicate, payment recorded, lock/unlock, rejected over-payment attempts. Shown as status history on order detail.

Financial-engineering signals (deliberate, README-visible)

  1. Money value object, minor-units representation (Stripe pattern); no floats anywhere in DB or math.
  2. Rounding policy stated as mode + boundary: half-up, per line, 2 dp. Penny-allocation (largest remainder) acknowledged in README as known territory.
  3. payments treated as a ledger: append-only (no update/delete endpoints), balances always derived, refunds = negative entries (stretch). Double-entry deferred to README "what I'd improve".
  4. Idempotency-Key header on payment creation; replay returns the original 201.
  5. Over-payment check re-reads the paid sum inside a transaction.
  6. Finalize freezes a totals snapshot; corrections via duplicate-to-new-draft (reversing-entry pattern) — implement this stretch goal.
  7. Locking = period close, enforced by one server-side guard on every planner write path.

API design

Every handler: auth → validate → load + ownership check → business-rule guard → transaction (write + audit) → return server-computed state. Client never sends totals.

Error envelope: { "error": { "code", "message", "details?" } }
Codes: 400 validation (Zod field errors in details), 401, 404 (not found or not owned — no existence leak), 409 business conflicts: DOCUMENT_FINALIZED, OVER_PAYMENT (message includes max allowed), PERIOD_LOCKED.

Endpoints:

  • Pricing: CRUD documents + nested line-items; POST /documents/:id/finalize; POST /documents/:id/duplicate; GET /report?from&to.
  • Orders: CRUD orders (lines replaced wholesale on PUT while editable); POST /orders/:id/payments; GET /orders?status=; detail includes payments + audit history.
  • Planner: categories CRUD; PUT /plans upsert; actuals CRUD; POST /actuals/import (CSV, all-or-nothing, row-numbered errors); POST /locks, DELETE /locks/:month; GET /report?from&to.

Documented edge-case choices

  • Fixed discount > line subtotal → reject (validation error), not clamp.
  • Both discount types set → reject.
  • Overdue order paid in full → paid (paid wins over overdue).
  • Plan = 0 → variance% null, rendered "—".
  • Missing actual → "—" for Actual/Variance/Variance% (consistent).
  • Orders remain editable until first payment, then lines become read-only (documented).

Frontend

Central API client parses the envelope: 400 field errors map inline to form inputs; 409/other errors → sonner toast with the server's actionable message; success toasts on mutations. Recharts chart on planner report (monthly net variance). Print stylesheet for pricing printable view. Seed script loads each spec's sample data so evaluators land on meaningful screens.

Testing

  • calc/pricing must reproduce the spec sample exactly: subtotal 450.00, discount 40.00, tax 11.50, grand total 421.50 (per-line 189.00 / 52.50 / 180.00).
  • calc/orders status transitions incl. the $1,000 → $400 → $600 → reject-$1 scenario.
  • calc/planner variance table from spec sample; plan=0 and missing-actual cases.
  • API guard tests: finalized-immutability, over-payment (incl. idempotent replay), period-lock.

Deployment ($0)

Vercel Hobby + Turso free tier. Env: TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, BETTER_AUTH_SECRET via vercel env. Migrations via drizzle-kit. One URL with landing page; README per app (setup, rounding policy with worked example, lifecycle/locking rules, assumptions, production improvements, live URL).
